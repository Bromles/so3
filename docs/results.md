# Результаты проверок

Этот файл фиксирует уже выполненные проверки и правила их интерпретации после смены концепции проекта.
SO3 рассматривается как proof of concept, поэтому результаты нужны для оценки работоспособности архитектуры, а не для
продуктового сравнения с готовыми S3-совместимыми системами.

Последняя локальная проверка Maelstrom: 2026-05-22 на macOS, один физический хост c M4 Pro.
Последняя локальная проверка k6: 2026-05-17 на macOS, один физический хост c M4 Pro.

## Как интерпретировать результаты

- Абсолютные значения пропускной способности и задержек не являются заявлениями о производительности SO3.
- Сравнение с MinIO/Garage не используется как критерий успеха: зрелые продукты ожидаемо быстрее прототипа,
  потому что SO3 не оптимизировался.
- Корректность конкурентов не проверяется и не обсуждается: они не являются предметом исследования.
- Исторические k6-цифры полезны как базовая проверка и исходный уровень самого SO3 для последующей нормализации.
- Новые нагрузочные проверки должны фокусироваться на динамике SO3: `after_fault / before_fault`,
  `during_recovery / baseline`, задержки горячего ключа против независимых ключей, разброс между запусками.

Подробный план дальнейших экспериментов находится в [research-plan.md](research-plan.md).

## Команды базовой проверки

Сборка:

```bash
cargo build --release -p so3 -p so3-maelstrom
```

Maelstrom:

```bash
uv run python scripts/maelstrom/smoke.py
uv run python scripts/maelstrom/smoke_3node.py
uv run python scripts/maelstrom/fault_3node.py
```

k6 baseline для SO3:

```bash
uv run python scripts/k6/run-backend-benchmark.py --backend so3 --runs 30 --outdir /tmp/so3-k6-backend-clean-30-json
uv run python scripts/k6/run-backend-benchmark.py --backend so3-cluster --runs 30 --outdir /tmp/so3-cluster-k6-clean-30-json
```

## Maelstrom

Бинарный файл: `target/release/so3-maelstrom`.
Workload: `lin-kv`.
Checker: strict-serializable / Knossos linearizability.

| Smoke    | 1    | 10 s  | 20   | `2n`        | none           | 197 | 144 |   53 |    0 |       0.731 | true  |
| Smoke    | 3    | 10 s  | 10   | `2n`        | none           |  95 |  67 |   28 |    0 |       0.705 | true  |

Файлы результатов:

| Сценарий     | Путь к результату                                   |
|--------------|-----------------------------------------------------|
| Smoke 1-node | `store/lin-kv/20260505T231122.384+0300/results.edn` |
| Smoke 3-node | `store/lin-kv/20260505T231151.117+0300/results.edn` |
| Fault 3-node | `store/lin-kv/20260505T231219.289+0300/results.edn` |

Интерпретация:

- все три запуска вернули `:valid? true`;
- `fail` ожидаем для чтений отсутствующих ключей/CAS и CAS precondition failures при конкуренции;
- partition-запуск включает nemesis-операции типа `info`;
- это результаты Maelstrom-адаптера; каждый Maelstrom-узел теперь координирует клиентские запросы локально,
  но адаптер по-прежнему не покрывает все production-сценарии (blob-валидация, CAS-атомарность, дедлайны);
- Maelstrom остается полезным smoke-инструментом для safety/correctness, но не закрывает весь PoC-план из
  [research-plan.md](research-plan.md).

## k6 baseline SO3

Подробные отчеты по SO3-прогонам вынесены в отдельные файлы:

| Отчёт                                                 | Что содержит                                                    | Текущий статус интерпретации |
|-------------------------------------------------------|-----------------------------------------------------------------|------------------------------|
| [docs/so3-results.md](so3-results.md)                 | однонодовый `so3`, агрегаты и таблица 30 запусков               | baseline самого прототипа    |
| [docs/so3-cluster-results.md](so3-cluster-results.md) | кластер из трёх процессов `so3`, агрегаты и таблица 30 запусков | baseline самого прототипа    |

Базовый профиль k6 для SO3: 10 VU, 30 запусков по 30 секунд, объекты по 64 байта, цикл
`putObject -> getObject -> HEAD Object -> deleteObject`. Каждый запуск выполнялся на чистой директории данных.

Этот профиль является микробенчмарком согласованного пути на малых объектах. Он намеренно неблагоприятен для прототипа:
полезная нагрузка составляет всего 64 байта, поэтому результат в основном измеряет цену HTTP/RPC/metadata/consensus на
каждую операцию, а не пропускную способность дисковой или сетевой подсистемы.

Выводы:

- трехнодовый локальный кластер SO3 медленнее однонодового режима, что ожидаемо из-за consensus/RPC/replication пути;

## Исследовательские сценарии (реализованы)

Все приоритетные отчеты, необходимые для PoC, теперь генерируются автоматически исследовательским раннером
`scripts/research/run-scenario.py`. Каждый сценарий создаёт директорию с результатами, включая графики, сводный
`report.md` и нормализованные метрики.

Соответствие между прежними запланированными отчётами и командами запуска:

| Прежний отчёт                        | Команда                                                          | Что генерируется                                                                                                                                          |
|--------------------------------------|------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| `so3-failure-degradation-results.md` | `run-scenario.py e3-degradation`                                 | Графики, `report.md` с пофазовой сводкой (baseline → fault → degraded → recovery), временная шкала, нормализованные метрики                               |
| `so3-hot-key-results.md`             | `run-scenario.py e4-hot-key`                                     | Сравнение задержек горячего ключа против независимых ключей, отношение p95                                                                                |
| `so3-failure-symmetry-results.md`    | `run-scenario.py e3-degradation --fault-node-policy round_robin` | График симметрии: отказ каждого узла по очереди, сравнение нормализованной деградации                                                                     |
| `so3-recovery-results.md`            | `run-scenario.py e6-recovery`                                    | Поведение при восстановлении: накопленное отставание, задержки в процессе, доля успешных и таймаутовых операций, верификация sentinel, время стабилизации |
| `so3-multi-entrypoint-results.md`    | `run-scenario.py e5-leaderless`                                  | Распределение запросов по точкам входа (per-node entry distribution), проверка отсутствия скрытого лидера                                                 |

Все сценарии используют относительные метрики и проверку инвариантов из [research-plan.md](research-plan.md).

Полное описание методологии, формата и интерпретации результатов — в [docs/research-results.md](research-results.md).
