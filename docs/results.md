# Результаты проверок

Последняя локальная проверка Maelstrom: 2026-05-15 на macOS, один физический хост c M4 Pro.
Последняя локальная проверка k6: 2026-05-17 на macOS, один физический хост c M4 Pro.

## Команды

Сборка:

```bash
cargo build --release -p so3 -p so3-maelstrom
```

Maelstrom:

```bash
BINARY_PATH=target/release/so3-maelstrom NO_BUILD=1 bash scripts/maelstrom/smoke-lin-kv.sh
BINARY_PATH=target/release/so3-maelstrom NO_BUILD=1 bash scripts/maelstrom/smoke-3-node-lin-kv.sh
BINARY_PATH=target/release/so3-maelstrom NO_BUILD=1 bash scripts/maelstrom/fault-3-node-lin-kv.sh
```

k6 S3 benchmark:

```bash
python scripts/k6/run-backend-benchmark.py --backend so3 --runs 30 --outdir /tmp/so3-k6-backend-clean-30-json
```

Базовый профиль k6 одинаков для всех строк сводки ниже: 10 VU, 30 запусков по 30 секунд, объекты по 64 байта, цикл
`putObject -> getObject -> HEAD Object -> deleteObject`. Каждый запуск выполнялся на чистой директории данных или чистом
Docker Compose project.

Этот профиль является микробенчмарком согласованного пути на малых объектах. Он намеренно неблагоприятен для прототипа:
полезная нагрузка составляет всего 64 байта, поэтому результат в основном измеряет цену HTTP/RPC/metadata/consensus на
каждую операцию, а не пропускную способность дисковой или сетевой подсистемы. Поэтому его корректнее использовать как
стресс-тест latency и coordination overhead, а не как единственную оценку продуктовой производительности. Для более
полной оценки стоит добавить отдельные профили: larger-object throughput, read-heavy workload и mixed workload с
повторным чтением уже записанных объектов.

### Обоснование нефункционального требования производительности

MinIO и Garage используются как внешний промышленный ориентир, а не как требование полного паритета для прототипа. В
согласованных многонодовых режимах они показывают 435.7–544.4 S3 запросов/с на том же локальном стенде. Текущий `so3`
cluster показывает 81.2 S3 запросов/с, то есть примерно 18.6% от `minio-distributed` и 14.9% от
`garage-consistent`. Это означает, что прототип пока не является производительной заменой промышленным S3-compatible
хранилищам, но достигает воспроизводимого интерактивного уровня при нулевой доле ошибок.

Для работы это можно зафиксировать как минимальное нефункциональное требование к прототипу:

| ID         | Требование                                                              |              Порог | Факт `so3` cluster | Статус    |
|------------|-------------------------------------------------------------------------|-------------------:|-------------------:|-----------|
| NFR-PERF-1 | Средняя пропускная способность кластера из 3 узлов в базовом k6-профиле | ≥ 75 S3 запросов/с |            81.2452 | выполнено |
| NFR-PERF-2 | Доля ошибок S3 в базовом k6-профиле                                     |               < 1% |             0.0000 | выполнено |
| NFR-PERF-3 | Средний по запускам `PUT p95`                                           |           ≤ 300 ms |          264.69 ms | выполнено |
| NFR-PERF-4 | Средний по запускам `GET p95`                                           |           ≤ 200 ms |          171.64 ms | выполнено |
| NFR-PERF-5 | Средний по запускам `HEAD p95`                                          |           ≤ 200 ms |          179.83 ms | выполнено |
| NFR-PERF-6 | Средний по запускам `DELETE p95`                                        |           ≤ 250 ms |          223.86 ms | выполнено |

Порог 75 S3 запросов/с выбран как нижний воспроизводимый уровень для исследовательского прототипа: он составляет около
17.2% от худшего промышленного согласованного baseline (`minio-distributed`, 435.7 запросов/с), а фактический результат
`so3` cluster превышает этот порог с запасом относительно 95% доверительного интервала среднего (`81.2452 ± 2.6744`
запросов/с).

### Интерпретация

- Трёхнодовый `so3` cluster дал 81.2 S3 запросов/с, то есть 56.6% от однонодового результата `so3` (-43.4%). Основной
  вклад в просадку даёт запись: средний `PUT` вырос с 87.31 до 178.39 ms (2.04×), `DELETE` — с 69.48 до 121.64 ms
  (1.75×).
- В абсолютных числах локальные согласованные backend-ы расположились так: `garage-consistent` — 544.4 S3 запросов/с,
  `minio-distributed` — 435.7 S3 запросов/с, `so3` cluster — 81.2 S3 запросов/с.
- `garage-consistent` в этом локальном стенде быстрее `minio-distributed` по общей пропускной способности: 544.4 против
  435.7 S3 запросов/с, примерно +25%.
- У `minio-distributed` очень дешёвые чтения (`GET`/`HEAD` около 2–3 ms), но дорогой хвост и среднее значение `PUT`
  (`avg` 77.09 ms, `p95` 315.22 ms). На этом сценарии запись доминирует общий темп.
- У `garage-consistent` запись и удаление заметно ровнее (`PUT avg` 27.67 ms, `p95` 48.50 ms; `DELETE avg` 27.24 ms,
  `p95` 48.35 ms), но согласованные чтения дороже, чем у single-node Garage.
- Производительность `so3` существенно ниже промышленных аналогов. Это ограничивает применимость текущей реализации
  сценариями с невысокой интенсивностью запросов, где приоритетом является согласованность и простота модели, а не
  максимальная пропускная способность. Для production-нагрузок нужны дополнительные работы: оптимизация read path,
  batching consensus-команд, кэширование metadata, распределение клиентской нагрузки между S3-нодами, оптимизация
  журнала консенсуса и blob-репликации.
- Все сравнения запускались на одном физическом хосте, поэтому это не сетевой multi-host benchmark: цифры в первую
  очередь отражают локальные накладные расходы координации/репликации. Для MinIO/Garage это Docker-контейнеры, для
  `so3` cluster — три локальных процесса `target/release/so3`.
