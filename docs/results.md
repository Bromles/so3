## Команды

Сборка:

```bash
cargo build --release -p so3 -p so3-maelstrom
```

```bash
BINARY_PATH=target/release/so3-maelstrom NO_BUILD=1 bash scripts/maelstrom/smoke-lin-kv.sh
BINARY_PATH=target/release/so3-maelstrom NO_BUILD=1 bash scripts/maelstrom/smoke-3-node-lin-kv.sh
BINARY_PATH=target/release/so3-maelstrom NO_BUILD=1 bash scripts/maelstrom/fault-3-node-lin-kv.sh
```

```bash
bash scripts/k6/run-benchmark.sh --runs 30 --outdir /tmp/so3-k6-clean-30-json
```

## k6 S3 benchmark

Бинарный файл: `target/release/so3`.
Конфигурация: 10 VU, 30 запусков по 30 секунд, объекты по 64 байта. Каждая итерация выполняет
S3-операции `putObject -> getObject -> HEAD Object -> deleteObject`: `putObject`, `getObject` и
`deleteObject` вызываются через k6 S3Client, а `HEAD Object` выполняется прямым HTTP `HEAD` к
S3-совместимому endpoint, потому что в используемом клиенте нет отдельного `headObject`.

Каждый k6-запуск был чистым: `scripts/k6/run-benchmark.sh` перед каждым прогоном запускал новый
release-процесс `so3` с новой временной `SO3_DATA_DIR=/tmp/so3-k6-run-*`, после прогона останавливал
процесс и удалял директорию данных. Поэтому агрегаты ниже не включают накопленные данные и фоновые
накладные расходы от предыдущих прогонов.

Статистика ниже рассчитана по 30 независимым запускам. `σ` — стандартное отклонение,
`стандартная ошибка` и `95% ДИ` — оценки неопределённости среднего; `коэф. вариации` —
коэффициент вариации, то есть относительный разброс. Дисперсия считается как выборочная
(`n - 1` в знаменателе); `95% ДИ` использует t-критическое значение для 29 степеней свободы.
Для метрик задержки агрегируются значения, которые k6 посчитал внутри каждого отдельного запуска.

Заметки:

- `scripts/k6/run-benchmark.sh` параллельно снимает CPU/RSS и печатает агрегаты ресурсов.
- Benchmark запускает и останавливает `target/release/so3` сам; для опубликованных чисел не использовался
  долгоживущий процесс и общая директория данных.
- k6-скрипт использует локальную копию клиента Grafana S3 в `scripts/k6/lib/s3.js`.
- macOS `%cpu` считает 100% как одно логическое ядро, поэтому 118.04% означает примерно 1.18 ядра в среднем.
- S3 `getObject` и `HEAD Object` сейчас координируют команды `Read` через consensus coordinator; это не локальные
  metadata-only чтения.
