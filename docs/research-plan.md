# План исследовательской проверки SO3

SO3 рассматривается как экспериментальный proof of concept, а не как готовое объектное хранилище.
Цель проверок — показать, что Accord-подобный безлидерный консенсус применим для реализации объектного хранилища и
что прототип имеет смысл развивать дальше.

## Что не доказывается

- SO3 не сравнивается по абсолютной производительности со зрелыми системами.
- Корректность конкурентов не тестируется: они считаются промышленно отлаженными системами и не являются предметом
  работы.
- Абсолютные значения пропускной способности и задержек не используются как продуктовые заявления.
- Полная S3-совместимость, промышленная надёжность хранения, оптимизированный уровень данных и эксплуатационная
  готовность находятся вне текущего scope.

## Главная гипотеза

Accord-подобный безлидерный протокол можно использовать как основу для уровня метаданных и управления объектного
хранилища: операции над объектами остаются корректными, система сохраняет безопасность при допустимых отказах,
деградирует предсказуемо, локализует конфликты и не имеет постоянного лидера как узкого места.

## Что нужно доказать

| Направление             | Проверяемое свойство                                                                                        |
|-------------------------|-------------------------------------------------------------------------------------------------------------|
| Correctness             | `PUT`, `GET`, `HEAD`, `DELETE`, overwrite и условные операции не нарушают object-level инварианты           |
| Fault safety            | Crash, restart и partition не приводят к противоречивым committed состояниям                                |
| Liveness при кворуме    | При наличии кворума операции продолжают завершаться, пусть и медленнее                                      |
| Predictable degradation | Под отказами задержки и пропускная способность меняются объяснимо и повторяемо относительно базового уровня |
| Conflict behavior       | Горячий ключ ухудшает конфликтующую область, но не вызывает глобальный коллапс независимых ключей           |
| Leaderless behavior     | Нет узла, отказ которого выглядит как отказ постоянного лидера                                              |
| Recovery                | Отставший узел догоняет состояние без потери подтверждённых записей и без перезаписи новых данных старыми   |
| Observability           | Внутренние метрики позволяют объяснить, почему система перешла на быстрый/медленный путь или восстановление |

## Основные инварианты корректности

Object-level инварианты:

1. `GET` не возвращает значение, которое никогда не было успешно записано.
2. После successful `PUT` объект имеет записанную или более позднюю версию.
3. После successful `DELETE` старая версия не возвращается как текущая.
4. Две успешные конфликтующие записи имеют объяснимый порядок.
5. `PUT if-match` или аналогичная CAS-операция успешна только при совпадении ожидаемой версии.
6. `PUT if-none-match` успешен только если объект действительно отсутствовал.
7. Повтор операции с тем же request/idempotency key не создает независимое второе изменение.
8. После восстановления подтверждённые записи остаются видимыми.

Cluster-level инварианты:

1. Minority partition не может закоммитить конфликтующую запись без кворума.
2. Узел после recovery не может вернуть старое состояние как актуальное.
3. Replay сообщений не меняет уже принятое решение некорректно.
4. Metadata не должна ссылаться на отсутствующий или неполный committed blob.
5. После heal partition реплики сходятся.

## Методика нагрузочных проверок

Нагрузочные тесты нужны не для ответа «сколько ops/sec выдерживает продукт», а для ответа «как ведет себя прототип при
сбоях, восстановлении и конфликтах». Поэтому основной формат результатов — относительные и динамические метрики:

| Метрика                   | Интерпретация                                            |
|---------------------------|----------------------------------------------------------|
| Throughput ratio          | `throughput_scenario / throughput_baseline`              |
| Latency multiplier        | `p95/p99_scenario / p95/p99_baseline`                    |
| Success ratio             | `successful_ops / attempted_ops`                         |
| Timeout ratio             | `timeouts / attempted_ops`                               |
| Stabilization time        | Время от момента отказа до нового устойчивого состояния  |
| Recovery time             | Время от возврата узла до устойчивого нормального режима |
| Run-to-run variance       | Повторяемость одинакового сценария                       |
| Hot/independent key ratio | Насколько конфликт влияет на независимые ключи           |

Абсолютные числа можно сохранять для воспроизводимости окружения, но выводы должны формулироваться через динамику,
отношения, форму графиков и прохождение инвариантов.

## Минимальный набор экспериментов

### E1. Correctness under concurrency

Цель: доказать, что объектные операции поверх Accord-подобной координации корректны без fault injection.

Сценарии:

- concurrent `PUT` по разным ключам;
- concurrent overwrite одного ключа;
- concurrent `PUT`/`DELETE`;
- `GET`/`HEAD` во время записей;
- условные операции и CAS-like сценарии;
- retry после timeout, если поддерживается idempotency key.

Результат: история операций проходит верификатор или набор инвариантов объектного уровня.

### E2. Fault safety

Цель: доказать, что сбои не ломают safety.

Сценарии:

- crash coordinator во время операции;
- crash replica до/после commit;
- crash после commit до client ack;
- restart узла;
- network partition majority/minority;
- heal partition.

Результат: нет противоречивых committed состояний, minority не принимает unsafe writes, после восстановления состояние
сходится.

### E3. Degradation under node failures

Цель: показать предсказуемую динамику при отказах.

Сценарий:

1. базовый уровень под стабильной нагрузкой;
2. отказ одного узла;
3. деградированный устойчивый режим;
4. восстановление узла;
5. синхронизация состояния;
6. возврат к нормальному режиму.

Повторить для 3-, 5- и 7-node конфигураций, если они поддерживаются тестовым стендом.

Результат: нормализованные задержки и пропускная способность меняются повторяемо; нет необъяснимых остановок и операций,
зависших навсегда.

### E4. Конкуренция за горячий ключ

Цель: проверить старый риск безлидерных протоколов — деградацию при высокой конкуренции за объект.

Сценарии:

- равномерное распределение ключей;
- 100% записей в один объект;
- 90% записей в один объект и 10% независимых ключей;
- распределение Zipf;
- шторм условных записей по одной версии.

Результат: конфликтующий ключ деградирует объяснимо, независимые ключи продолжают работать, метрики зависимостей,
повторов и медленного пути не растут бесконечно.

### E5. Отсутствие скрытого лидера

Цель: показать, что прототип не имеет постоянного лидера как единственной точки координации.

Сценарии:

- клиенты подключаются к разным узлам;
- операции координируются разными узлами;
- каждый узел по очереди выключается;
- сравнивается деградация при отказе каждого узла.

Результат: нет узла, отказ которого принципиально хуже остальных; нет паузы выбора лидера; метрики координации
и нагрузки по каждому узлу распределены.

### E6. Восстановление и отставший узел

Цель: проверить безопасное возвращение отставшего узла.

Сценарии:

- узел выключен на короткое время;
- узел выключен на долгое время;
- узел возвращается под нагрузкой;
- узел снова падает во время синхронизации.

Результат: подтверждённые записи не теряются, старое состояние не перезаписывает новое, восстановление оказывает
измеримый, но ограниченный эффект на клиентские операции.

## Рекомендуемые графики для отчета

1. Хронология отказа: нормализованные p95/p99 задержки и пропускная способность во времени с отметками `fail`,
   `degraded`, `recover`.
2. Повторяемость: несколько одинаковых прогонов с отказами на одном графике.
3. Изоляция горячего ключа: задержки операций с горячим ключом против задержек независимых ключей.
4. Симметрия отказов: коэффициент деградации при отказе каждого узла по очереди.
5. Восстановление: накопленное отставание, доля успешных операций и задержки в процессе восстановления.
6. Метрики путей Accord: доля быстрого/медленного пути и пути восстановления, частота конфликтов, глубина зависимостей,
   количество повторов.

## Что нужно логировать

На стороне клиента:

- идентификатор операции и idempotency key;
- тип операции;
- ключ, версия, хеш значения;
- временные метки начала и конца;
- код результата, таймаут или ошибка;
- входной узел.

На стороне сервера:

- координирующий узел;
- время фаз (`PreAccept`, `Accept`, `Commit`, `Apply`, `Recover`);
- время ожидания кворума;
- быстрый путь / медленный путь / путь восстановления;
- количество конфликтов, зависимостей, повторов;
- участвующие реплики;
- результат commit/apply.

На уровне кластера:

- состояние узлов (живые/упавшие);
- состояние сетевого раздела;
- очередь и незавершённые операции;
- накопленное отставание при восстановлении;
- CPU/RSS/сеть по каждому узлу, если доступно.

## Критерии успеха PoC

PoC успешен, если он показывает, что:

1. объектные операции проходят верификатор / инварианты корректности;
2. при наличии кворума система продолжает завершать операции;
3. при отсутствии кворума система не принимает небезопасные записи;
4. отказ узлов вызывает повторяемую, объяснимую деградацию относительно собственного базового уровня;
5. высокая конкуренция за горячий ключ локализуется и не валит независимые ключи;
6. нет постоянного лидера как узкого места;
7. восстановление отставшего узла безопасно;
8. оставшиеся ограничения понятны и могут быть оформлены как план оптимизации и усиления.
